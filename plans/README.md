# Android Vector Drawable Editor Plans

Generated by the improve skill on 2026-08-12 against commit `3268b817`.

The product target is an excellent editor for Android `VectorDrawable` and
`AnimatedVectorDrawable` resources. It is not a general Figma replacement.
Frames are Android asset/artboard containers: intrinsic dp size, viewport size,
vector alpha, and a drawable scene. Auto layout, hug/fill sizing, constraints,
text, components, prototyping, and collaboration are intentionally excluded.

## Dependency notes

- Plan 001 defines the fixtures and semantic contract every later migration must preserve.
- Plan 002 removes lossy V1/V2 project projections before more Android behavior is stored.
- Plan 003 makes the browser preview, hit testing, and compiler consume the same hierarchy and transforms.
- Plan 004 relies on the world matrices and evaluated geometry produced by Plan 003.
- Plan 005 relies on the canonical document and evaluated scene, then adds complete AVD timing/property semantics.
- Plan 006 is the release gate: imported XML, browser preview, exported resources, and an independent Android parser/compiler must agree.

## Product acceptance target

A release is Android-editor ready when all of the following are true:

1. A supported VectorDrawable XML file can be imported, edited, saved, reopened,
   and exported without semantic drift in hierarchy, viewport, path geometry,
   transforms, clipping, fill/stroke, trim, and supported gradients.
2. Every supported AnimatedVectorDrawable property previews using the same target,
   value, timing, ordering, and interpolator semantics that the generated Android
   resources declare.
3. Incompatible path morphs and unsupported Android features block export with
   actionable diagnostics; the UI never reports a knowingly degraded file as a
   successful production export.
4. The generated bundle can be copied directly into `res/drawable` and
   `res/animator` and passes independent Android resource compilation.
5. Direct editing, selection, bounds, clipping, and transforms remain correct for
   nested Android groups at any playhead position.

## Explicit non-goals

- Figma auto layout, hug contents, fill container, constraints, or responsive UI layout.
- Text layout, component systems, variables, multiplayer collaboration, or prototyping flows.
- A general SVG/CSS/Lottie/PDF authoring suite. Those exporters may remain, but must
  not drive the document model or block Android correctness work.
- Figma vector-network branching. Android `pathData` compatibility and predictable
  morph topology take priority over a more general network representation.
- Non-destructive Figma-style Boolean groups in this phase. Boolean commands may be
  disabled until a correct Android-path flattening kernel exists.

## Findings considered and rejected

- Figma frame auto layout and hug/fill sizing: unrelated to VectorDrawable assets.
- General Figma frames, effects, components, and layout constraints: unnecessary for the Android XML target.
- Editable spatial motion paths as a primary feature: Android group X/Y properties are useful, but path-following authoring is secondary to exact ObjectAnimator property tracks.
- Broad Lottie, PDF, animated SVG, and CSS parity: out of scope for the Android-first roadmap.
- Full Figma vector-network semantics: Android ultimately requires serializable `pathData`; prioritize Android-compatible node sequences and morph compatibility.
